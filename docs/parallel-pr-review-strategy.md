# 並行PR戦略におけるトークン最適化とレビュー方針

## 📋 はじめに

### 並行PR戦略とは

AI駆動開発では、執筆速度を最大化するために、複数のPull Request（PR）を同時進行で作成する「並行PR戦略」が有効です：

```
main (基本構造のみ)
 ├─ PR A: セクション A のみ
 ├─ PR B: セクション A + セクション B
 ├─ PR C: セクション A + セクション B + セクション C
 └─ PR D: セクション A + ... + セクション D (完結)
```

この戦略により、**執筆完了を待たずにレビューを開始**でき、開発サイクルが加速します。

### トークン最適化の重要性

しかし、この戦略には**トークン過剰消費**という重大な課題があります：

- すべてのPRが同じファイルを**累積的に**変更
- 各PRでセクション A を繰り返しレビュー
- 同じ内容を複数回処理する無駄が発生

本文書では、この課題を解決し、並行PR戦略の利点を最大化する方法を提示します。

---

## ⚠️ 並行PRの構造と問題点

### 2.1 累積的変更の構造

並行PRでは、各PRが**前のPRの内容を含む**構造になります：

| PR | 含まれるセクション | ファイルサイズ |
|----|------------------|--------------|
| PR A | セクション A | 小（例: 2KB） |
| PR B | セクション A + B | 中（例: 5KB） |
| PR C | セクション A + B + C | 大（例: 10KB） |
| PR D | セクション A + ... + D | 最大（例: 15KB） |

**特徴**: 後続のPRほどファイルサイズが大きくなる

---

### 2.2 潜在的問題（4点）

#### 問題1: トークンの過剰消費

**問題**:
- PR B でセクション A をレビュー
- PR C でも同じセクション A をレビュー
- PR D でも同じセクション A をレビュー
- **同じ内容を複数回処理**

**トークン消費の例**:
- セクション A（2KB）を4回レビュー = 8KB分の処理
- 実質的には1回（2KB）で済むはず
- **6KB分のトークンが無駄**

**コスト影響**:
- AI APIのコスト増加
- レートリミット到達が早まる
- レビュー時間の増加

---

#### 問題2: レビューの不一貫性

**問題**:
- PR B でセクション A に指摘X
- PR C では同じセクション A に指摘なし
- または、異なる指摘Y
- **どちらに従うべきか不明**

**混乱の発生**:
- 同じ文章に対して異なるフィードバック
- レビュー者（AI）も混乱
- 修正方針が定まらない

---

#### 問題3: マージ競合

**問題**:
- すべてのPRが同じファイルを変更
- マージ順序により競合（conflict）が発生

**シナリオ**:
1. PR B をマージ（セクション A + B が main に入る）
2. PR C をマージしようとする
   - PR C のbase: 古い main
   - 現在の main: セクション A + B あり
   - → **競合発生**

**必須対応**:
- PR A → B → C → D の**順番でマージ**
- マージ前に各ブランチを main にリベース

---

#### 問題4: レビュー負担の増加

**問題**:
- 各PRのサイズが累積的に増加
- 後続のPRほどレビュー負担が大きい
- 「どこが新規追加か」の特定が必要

**レビュー時間の例**:
- PR A: 2KB（新規のみ）
- PR B: 5KB（うち2KBは既存）
- PR D: 15KB（うち13KBは既存）
- **累積的にレビュー時間が増加**

---

## 🎯 解決策（3案）

### A案: レビュー方針の明確化（推奨）

#### 方針

**各PRで新規追加部分のみをレビュー**することを明示

#### 実施方法

**1. PR作成者の責任**:
- PR descriptionに「新規追加部分」を明記
  - 例: 「新規追加: セクション B のみ（L50-L100）」
- 既存部分（前のPRと重複）を明示
  - 例: 「既存部分: セクション A（L1-L49、PR A でレビュー済み）」

**2. レビュー者の責任**:
- 新規追加部分のみをレビュー
- 既存部分（前のPRでレビュー済み）はスキップ
- 必要に応じて「全体の流れ」を軽く確認（オプション）

**3. マージ方針**:
- PR番号順でマージ（A → B → C → D）
- マージ前に各ブランチを main にリベース（必要に応じて）

---

#### メリット

✅ **並行作業を維持**: 執筆速度が速い  
✅ **トークン消費を削減**: 新規部分のみレビュー  
✅ **レビューの一貫性**: 各セクションは1回のみレビュー  
✅ **実装が容易**: ルール追加とPR description改善のみ

---

#### デメリット

❌ **新規部分の特定負担**: レビュー者が新規部分を把握する必要  
❌ **マージ順序の制約**: 順番にマージする必要

---

#### トークン削減効果

**削減例**:
- PR B: セクション A（2KB）をスキップ、セクション B（2KB）のみレビュー
- PR C: セクション A + B（4KB）をスキップ、セクション C（3KB）のみレビュー
- PR D: セクション A + B + C（7KB）をスキップ、セクション D（3KB）のみレビュー

**合計削減**: 約13KB分のトークン削減（4PR合計）

---

### B案: 連鎖的ブランチ戦略

#### 方針

各PRを前のPRから分岐させる：

```
main
 └─ PR A (セクション A のみ)
     └─ PR B (セクション B のみ) ← PR A から分岐
         └─ PR C (セクション C のみ) ← PR B から分岐
```

---

#### メリット

✅ **各PRは新規部分のみ**: トークン消費が最小  
✅ **レビューの一貫性**: 自然に確保  
✅ **マージ競合回避**: 発生しにくい

---

#### デメリット

❌ **並行作業が不可能**: 前のPRマージ待ち  
❌ **執筆速度が遅くなる**: 最大の欠点  
❌ **既存PRの作り直し**: 大きな手戻り

---

### C案: レビュー範囲の段階的制限

#### 方針

各PRで新規追加部分のみをレビュー（厳密版）：

- PR A: セクション A をレビュー
- PR B: **セクション B のみ**をレビュー（セクション A は完全スキップ）
- PR C: **セクション C のみ**をレビュー（セクション A, B は完全スキップ）

---

#### メリット

✅ **トークン消費を大幅削減**: 最も効率的  
✅ **レビュー負担を軽減**: 最小限の作業  
✅ **並行作業を維持**: 執筆速度を保つ

---

#### デメリット

❌ **全体の流れを確認できない**: セクション間の接続が見えない  
❌ **文脈の理解が困難**: 前後関係を把握しにくい

---

### 推奨案の選択

**A案（レビュー方針の明確化）**を推奨します。

**理由**:
1. **既存の並行PR構造を維持**（作り直し不要）
2. **並行作業を維持**（執筆速度を保つ）
3. **トークン消費を大幅削減**（新規部分のみレビュー）
4. **実装が容易**（ルール追加のみ）
5. **全体の流れも確認可能**（オプションとして）

---

## 📖 実践ガイド

### 4.1 PR作成時のチェックリスト

#### 必須項目

- [ ] PR descriptionに「新規追加部分」を明記
- [ ] セクション名または行範囲を指定
- [ ] 概算サイズを記載（KB または文字数）
- [ ] 既存部分を明示（どのPRでレビュー済みか）

---

#### 記述例

```markdown
## 🆕 新規追加部分（レビュー対象）

- **新規追加**: セクション B（L50-L100、約2KB）
- **既存部分**: セクション A（L1-L49、PR A でレビュー済み）

## 📋 レビュー依頼

新規追加部分（セクション B）のみをレビューしてください。

既存部分（セクション A）は PR A でレビュー済みのため、
再レビューは不要です。

必要に応じて「セクション A → B の流れ」を軽く確認してください（オプション）。
```

---

### 4.2 レビュー時のチェックリスト

#### レビュー者の責任

- [ ] PR descriptionで新規追加部分を確認
- [ ] 新規追加部分のみを詳細にレビュー
- [ ] 既存部分は基本的にスキップ
- [ ] 必要に応じて全体の流れを軽く確認（オプション）
- [ ] レビューコメントに対象範囲を明記

---

#### レビューコメントの例

✅ **推奨**:
```markdown
## セクション B のレビュー

【良い点】
- ロジックが明確
- 例が適切

【改善提案】
- L75: 引用を追加すべき
```

❌ **非推奨**:
```markdown
## 全体のレビュー

セクション A: ... ← スキップすべき
セクション B: ... ← これのみレビュー
```

---

### 4.3 マージ時のチェックリスト

#### マージ前の確認

- [ ] PRが番号順でマージされているか確認
- [ ] 必要に応じてブランチをリベース
- [ ] 競合が発生していないか確認
- [ ] すべてのレビューが完了しているか確認

---

## 🔄 継続的改善

### 5.1 この方針自体も改善される

**初期運用**:
- 本文書の方針に従ってPRを作成・レビュー

**フィードバック収集**:
- 「新規部分の特定が困難」
- 「全体の流れが見えにくい」
- 「この方針では不十分」

**改善実施**:
- PR templateの改善
- レビューガイドラインの追加
- ツールの導入（diff抽出等）

**次の運用**:
- 改善された方針で運用
- さらなるフィードバック収集

---

### 5.2 プロジェクト固有のカスタマイズ

本文書は一般的な方針を提示していますが、プロジェクトによって最適な方針は異なります：

#### カスタマイズの例

**小規模プロジェクト**:
- 並行PRは不要（順次作成で十分）
- レビュー方針も簡素化

**大規模プロジェクト**:
- 並行PRが必須（執筆量が多い）
- レビュー方針の厳密化が必要

**チーム開発**:
- 複数人での並行作業
- レビュー担当者の明確化

---

## 📊 期待効果

### トークン消費の削減

**削減率の例**:
- 4つの並行PR（セクション A-D）
- 従来: セクション A を4回レビュー → 8KB
- 改善後: セクション A を1回のみ → 2KB
- **削減: 75%**

---

### レビューの一貫性確保

**改善前**:
- 同じセクションに複数の異なるフィードバック
- どれに従うべきか不明

**改善後**:
- 各セクションは1回のみレビュー
- フィードバックが一貫

---

### レビュー効率の向上

**改善前**:
- PR D（15KB）を全体レビュー
- 時間: 長い

**改善後**:
- PR D の新規部分（3KB）のみレビュー
- 時間: 大幅短縮

---

### 運用の明確化

**改善前**:
- レビュー範囲が曖昧
- レビュー者が迷う

**改善後**:
- レビュー範囲が明確
- 全AIが同じ方針でレビュー

## 🎯 まとめ

### 並行PR戦略の原則

1. **新規追加部分のみをレビュー**: トークン最適化の核心
2. **PR descriptionに明記**: 新規部分と既存部分の明確化
3. **順番にマージ**: 競合回避のため
4. **継続的改善**: 運用を通じて方針を改善

### 適用場面

この方針は、以下の場面で特に有効です：

- ✅ 大規模な文書の執筆（章・節単位）
- ✅ 長期プロジェクト（複数週間以上）
- ✅ AI協調開発（複数AIでのレビュー）
- ✅ トークンコストが重要な場合

### 注意事項

この方針は、以下の場合には適用しないでください：

- ❌ 小規模な変更（1PR で完結）
- ❌ 緊急の修正（並行PR不要）
- ❌ 独立した複数ファイルの変更（競合なし）

### 最後に

**並行PR戦略は、AI駆動開発の強力な武器です。**

しかし、適切なレビュー方針がなければ、トークンの無駄遣いとレビューの混乱を招きます。

本文書の方針を採用し、並行PRの利点を最大化してください。

**そして、この方針自体も、使いながら改善してください。**
